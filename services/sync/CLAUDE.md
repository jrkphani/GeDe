# services/sync — conventions

Fastify 5 + `ws`. One process serves the y-websocket document rooms and the REST API.
Runs on ECS Fargate ARM64 behind an ALB; `/api/*` arrives via CloudFront, `wss://ws.gede.work` arrives directly.
Read the root `CLAUDE.md` first.

## Authentication and permission (SHARE-03)

- Every REST route under `/api` and every WebSocket upgrade verifies the Cognito **access** JWT (signature, issuer, client id, expiry) with `aws-jwt-verify`, then resolves the caller's permission on the target document server-side from `documents` + `shares` (+ `link_access`).
- REST carries the token as `Authorization: Bearer`. The WebSocket upgrade carries it as a subprotocol, `Sec-WebSocket-Protocol: gede.v1, bearer.<token>` (issue #32); the server selects `gede.v1` and never echoes the bearer entry. The subprotocol is the only transport: a `?token=` query parameter is not read (#63 removed the one-release fallback) and a socket without a `bearer.` entry closes 4401. The request serializer in `logger.ts` still redacts `token=` in URLs (defence in depth), and no log line may ever carry a token.
- The only unauthenticated routes are `GET /healthz` and `GET /api/health`, and they answer `{ ok }` only. There is no allowlist, no debug token, no `NODE_ENV` bypass.
- Two rate limits (#37, #42). Per address, on every route at `onRequest` (`ip-limit.ts`, `RATE_LIMIT_PER_IP_PER_MINUTE`): the only bound on callers with no, an invalid or a rotating token, including WebSocket upgrades (which carry the token in a subprotocol, so they are address-keyed only). Per verified user, on `/api` at `preHandler` after the auth hook (`@fastify/rate-limit`, `RATE_LIMIT_PER_MINUTE`, key `user:<id>` — never the bearer string). Both in memory, per task.
- `request.ip` is what one hop of `X-Forwarded-For` yields (`trustProxy` trusts the ALB and nothing further, so a forged leftmost entry never counts): on the direct `/ws/*` path that is the **real client**; on `/api/*`, which arrives CloudFront → ALB, it is the **CloudFront edge** — every user behind one POP shares that address bucket, which is why it is generous and the per-user limit is the precise one. Do not key anything else on `request.ip` for `/api` without reading this.
- `users.email` is never bound from an access token in this pool: the SPA sends access tokens, which carry no `email`, and `username` is a Cognito-generated UUID (`signInAliases: { email: true }` makes email a username _attribute_, not the username). `emailFromClaims` keeps its guards (`email_verified`, an email-shaped `username`) for a pool configured otherwise and returns `null` in production. The address arrives through `PATCH /api/me { idToken }`: the SPA presents its Cognito **ID** token once after sign-in, the service verifies it (`tokenUse: 'id'`, same `sub`, `email_verified`) and binds the address — never a client-claimed string. That binding converts pending invitations into shares (SHARE-02), so it must be Cognito's word.
- Sharing routes live in `routes/share.ts` (`README.md` lists them). Rules: any participant reads the sheet (a viewer gets names only — and the library's `ownerName` / `sharedBy.name` follow the same rule, #102: an address is shown to the owner and editors, never to a viewer); the owner and editors invite; the owner alone changes permissions, removes people, sets the link mode and stops sharing. A permission is resolved at upgrade and held on the socket, so an in-process change closes that user's sockets at once (`RoomManager.closeUser`: 4403 when removed, 1001 to reconnect and re-resolve otherwise) and marks the connection `revoked` so frames that arrive before the peer answers the close are refused; every connection is also re-resolved every `WS_PERMISSION_RECHECK_MS` (#104), so a change made on another task or by hand ends the socket within a minute, and a token past its `exp` closes 1001. Every share change writes its `audit_log` row (`share.*`) in the same transaction. Invitations: their own per-user budget (`RATE_LIMIT_INVITES_PER_HOUR`) counted after validation and the permission check; idempotent per (document, address) while one is pending; converted only while the inviter still holds what they granted (else withdrawn, `share.invite_withdraw`). Every conversion — sign-in, `PATCH /api/me`, the invitation link — goes through `convertOne`: the document row lock first, then the invitation re-read `FOR UPDATE` under it, so a withdrawal, a stop or a delete that commits first wins (#100). Link access: any level change re-mints the token and, like switching off, revokes `source = link` shares — and a share given by a link-sourced editor is a link share too (`inheritedSource`, #101), so the whole chain goes with the link. A document in the trash accepts no share change: its pending invitations are withdrawn by Delete, its link cannot be switched on, nothing converts on it (#112).
- Delete vs archive (LIB-D, ADR-031): `documents.ever_shared` is written only by the repository, inside the share transactions — set by every path that inserts a share (`add`, `redeemLink`, `accept`, the sign-in conversion) and by switching the link on; cleared by `remove`, `stop` and `setLinkAccess` once no share remains and the link is off; never by sending an invitation. Every share transaction, and the owner's Delete (`documents.tryDelete`), first takes the document row `FOR UPDATE` (`lockDocument`; lock order documents → invites/shares) — it conflicts with the `FOR KEY SHARE` a share insert holds through its foreign key, so "no share remains" is never evaluated beside an uncommitted share and Delete never lands beside an acceptance. `DELETE /api/documents/:id` answers 409 `shared` while it is true or the link is on, and 409 `sample` for the guided sample; archive (`POST …/archive`, `…/unarchive`) touches `archived_at` alone — no share, link or socket changes. A row is archived or deleted, never both (CHECK); soft delete clears the archive. The purge keys off `deleted_at` alone; archive never expires.
- Share mail goes through `mail/` (SES v2, `Deps.mail`, sender `no-reply@<WEB_ORIGIN host>`, display name GeDe; templates in `mail/templates.ts` follow DESIGN-SYSTEM §6). The row is the grant, the mail its notification (#121): a share or an invitation is written before its mail and stands whatever the send did; `mail/delivery.ts` answers `delivery: 'sent' | 'failed'`, logs a refused send by failure class and template (never the address) and counts it on `GeDe/Sync InviteMailFailures`; an accepted invitation mail is recorded as `invites.mail_sent_at` (null = never mailed, which the sheet shows with Resend after a reload too); `POST …/invites/:inviteId/resend` sends the same invitation again under the same budget and one resend per invitation per `RATE_LIMIT_RESEND_COOLDOWN_SECONDS`, whoever asks. While SES is in the sandbox only verified recipients receive mail, so in production every invitation to a new person is `failed` until production access is granted (Runbook §5, §15) — the invitation still converts on the invitee's first sign-in, and the sender can share the link.
- A socket with `view` permission receives the document stream; its update messages are dropped and counted. Awareness from view-only sockets is accepted.
- `sub` maps to `users.cognito_sub`; the row is created on first sight from the JWT claims (email, name), plus `tour_done_at` (ONB-03: set and cleared through `PATCH /api/me { tourDone }`, never read from a device). Nothing else about identity is stored.
- Account erasure (`DELETE /api/me`, #111, ADR-038): `users.erase` is one transaction — shares held go, sent invitations are withdrawn, invitation rows to the address are deleted, owned live documents go to their earliest editor (`document.transfer`) or lose their shares and are soft-deleted (`document.delete`; the sample flag is cleared first), `doc_updates.author_id` is nulled, the address is scrubbed from `audit_log.target`, and the row becomes a tombstone with `deleted_at` set and `cognito_sub` kept. The auth hook answers 403 `account_deleted` for a tombstone and the upsert never re-binds an address to one. The Cognito user is deleted afterwards through `Deps.identity` (`AdminDeleteUser`), wired only when `COGNITO_ERASE_IDENTITY` is `true`; a refusal is logged as `UserErasureIdentityFailures`. Audit rows keep the actor id.

## Wire protocol

- y-websocket: message type 0 = sync (step 1, step 2, update), type 1 = awareness. Encoded with `lib0` and `y-protocols`. The browser uses the stock `y-websocket` provider. The one GeDe addition is type 4, a server-to-client notice (`{ "code": "read-only" }`, sent once per view-only connection); it is documented in `src/ws/protocol.ts` and the SPA reads it through `provider.messageHandlers[4]`. Do not add others.
- One room per open document (`/ws/:docId`). One in-memory `Y.Doc` per room, evicted after idle. The process assumes it is one of many (fan-out is behind an interface) even though production runs one task today.
- Per-connection limits (#37, #99, ADR-037): sync messages, bytes and awareness each have a token bucket (`WS_UPDATES_*`, `WS_BYTES_*`, `WS_AWARENESS_*`); every frame costs its length from the bytes bucket on arrival, awareness included, and a second sync step 1 on a socket costs the document's size estimate; over the message or byte burst the socket is closed 4429, excess awareness is dropped. `ws` refuses a frame over `WS_MAX_UPDATE_BYTES` on its declared length (1009). A socket whose `bufferedAmount` exceeds `WS_MAX_BUFFERED_BYTES` (plus the step 2 it was sent on join, while that is still being written) is closed 1013 and terminated in the same step. An awareness frame over `AWARENESS_MAX_BYTES` is refused on its length before it is decoded. Per task: `WS_MAX_ROOMS`, `WS_MAX_SOCKETS` (1013) and `WS_MAX_SOCKETS_PER_USER` (4429).
- Every client update is decoded by the room itself (`Y.decodeUpdate`, then `Y.applyUpdate`), never by `y-protocols` (#105): a frame that is not the protocol or does not decode is refused whole with 1007, counted (`stats.malformed`) and never reaches the document, the log, another socket or stderr. A document has a ceiling: an update that would take the room's size estimate past `DOC_MAX_BYTES` is refused with 4413 (the SPA treats 44xx and 1009 as terminal).
- Every refusal is one structured line that is also a `GeDe/Sync` metric datapoint (`metrics.ts`, CloudWatch embedded metric format: `WsRefusals` by `Reason`, `WsRevocations`, `UserErasureIdentityFailures`). No metric filter to keep in step; an alarm reads the namespace.

## Persistence contract

1. Every incoming update is appended to `doc_updates(document_id, seq, update, author_id)` before it is fanned out.
2. Every 500 updates, after 5 minutes idle, or once `DOC_LOG_MAX_BYTES` have been appended since the last snapshot (#99), the room encodes `Y.encodeStateAsUpdate` to S3 `<DOCS_PREFIX><documentId>/<seq>.yjs`, writes a `snapshots` row, updates `documents.snapshot_key/snapshot_seq`, then prunes `doc_updates` up to that seq — under the document row lock and only when `seq` is greater than the committed `snapshot_seq`, no other task has committed since this writer loaded (or last committed), and every logged row in `(coversFrom, seq]` was appended by this writer (#39): the pointer never moves back and never past rows the snapshot does not contain. A refused commit marks the room superseded; the manager drops it (sockets get 1001, reconnect, resync) and the next join loads from storage. Two tasks writing one document stays unsafe until growth step 1 adds cross-task fan-out; this only bounds the damage.
3. Cold open = load the snapshot (if any) then replay `doc_updates` after `snapshot_seq`.
4. A new document's initial state (`seedNewDocument` in `@gede/core`: meta + one sheet) is written by `POST /api/documents` as snapshot seq 1, in the same transaction as the row. Clients never seed. The guided sample (ONB-01, `seedSampleWorkscape`) is written the same way by `SampleSeeder` (`sample.ts`) from the auth hook on an account's first request, under a per-owner advisory lock so racing tasks write one object; `documents_owner_sample_key` keeps it to one per owner. A failed seed degrades (`sampleDocumentId: null`, logged, retried next request) and never fails the request. The sample cannot be renamed, deleted or archived (409 `sample`).
5. Projection tables are written by the Projection Worker (`src/projection/`), debounced after every compaction, from the snapshot's bytes, replacing the document's rows in one transaction; they are never read to reconstruct a document. `--job reproject` rebuilds them.
6. The nightly purge (`--job purge`, EventBridge Scheduler → the jobs task definition) deletes documents soft-deleted for more than 30 days, per batch: read the expired rows, delete each one's S3 prefix outside any transaction (#109: the pool's 30 s idle-in-transaction timeout can never fire on a slow S3 call), then one short transaction deletes the rows whose objects went, audit row with `user_id` null. A sample is never purged and never enters the trash (migration 0010 CHECK, #114); `softDelete`, Delete All and the purge refuse it as well.

## Migrations

`@gede/db` migrations run on boot under `pg_advisory_lock`, as the master user (`PG*`) on a one-connection pool that is closed before the server listens. The same step bootstraps the least-privilege role the runtime pool then connects as (`PGAPPUSER`/`PGAPPPASSWORD`, #36, ADR-022): DML only, no DDL, no `TRUNCATE`, read-only on `__migrations`. A query that needs more than DML belongs in the bootstrap's grants, never in a master-user pool; `pg.live.test.ts` runs the whole repository as the app role so it fails there first. A failed migration or bootstrap exits non-zero; ECS restarts the task and the previous task definition stays live (circuit breaker). In production a missing `PGAPPUSER`/`PGAPPPASSWORD` is fatal; there is no fallback to the master user.

## Environment

Set by `infra/lib/stacks/service-stack.ts` (the names are the contract; change both sides in one PR):

| -------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `PORT`                                                               | Listen port (3000)                                                                |
| `PGHOST` `PGPORT` `PGUSER` `PGPASSWORD` `PGDATABASE`                 | Injected from the RDS master secret by ECS; migrations and bootstrap only         |
| `PGAPPUSER` `PGAPPPASSWORD`                                          | Injected from `gede/prod/db-app`; the runtime pool. Required in production        |

| `DOCS_BUCKET` `DOCS_PREFIX`                                          | Snapshot bucket and key prefix (`docs/`); the task role is scoped to it           |
| `WEB_ORIGIN`                                                         | CORS origin (`https://gede.work`)                                                 |
| `NODE_ENV`                                                           | `production` in the task                                                          |
| `LOG_LEVEL`                                                          | Optional; pino level, default `info`                                              |
| `PROJECTION_DEBOUNCE_MS`                                             | Optional; wait after a compaction before the projection write (1 s)               |

| `GEDE_VERSION`                                                       | Baked into the image by the `GEDE_VERSION` build arg (short git sha)              |

Locally, `PG*` point at a local PostgreSQL 17, `PGSSLMODE=disable`, and `PGAPPUSER` is unset (the runtime is the master user; the boot log says which). Read everything once in `config.ts` with `zod`; nothing else touches `process.env`. The SES sender is `no-reply@<WEB_ORIGIN host>`.

## Errors and logging

- Every error response is `{ error: { code, message, ref } }`. `code` is a stable snake_case string, `message` is plain English for the client, `ref` is the request id the client shows as `ref …` on error pages. Never leak stack traces or SQL.
- Logging is `pino` through `fastify.log` / `request.log`. No `console.*` (ESLint enforces it). Log the `ref`, never a token or an update payload.
- Graceful shutdown: on `SIGTERM` stop accepting connections, snapshot every dirty room, close sockets with code 1001, close the pool, exit within 25 s (ECS gives 30).

## Tests

- `buildServer(deps)` takes every external dependency (db repo, S3 store, SES mailer, JWT verifier) so tests inject fakes (`test/fakes.ts`: `FakeVerifier` with `issue`/`issueId`, `FakeSnapshotStore`, `FakeMailer` with `sent[]`). No live AWS in unit tests; no network in `vitest`.
- `src/repo/pg.live.test.ts` runs the real SQL against a throwaway database when `DATABASE_URL` is set and is skipped otherwise. Add a case there whenever `pg.ts` gains a query the fake mirrors.
- Test names start with the requirement id: `test('SHARE-03 view-only socket updates are dropped', …)`.
- WebSocket tests use a real `ws` client against an ephemeral port.

## Container

`Dockerfile` targets `linux/arm64` on `node:22-alpine` and is built by CodePipeline. Never `docker push` an image by hand; the pipeline tags and deploys. `docker build --platform linux/arm64 -f services/sync/Dockerfile .` is a valid local check.
