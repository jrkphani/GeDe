# infra — conventions

One CDK v2 app (`bin/gede.ts`, run with `tsx`): `PipelineStack` (`GeDe-Pipeline`) that deploys
`GedeStage` (`GeDe-Prod-*`: Network, Data, Auth, Edge, Service, Web, Dns, Ops). Read the root
`CLAUDE.md` first; `docs/ARCHITECTURE-DIGEST.md` §1.4–1.7 is the source for every sizing
decision here.

## Rules

1. **Nobody runs `cdk deploy` from a laptop.** The one exception is the one-time bootstrap in
   `README.md`. After that the pipeline self-mutates: merge to `main` and CodePipeline `GeDe`
   applies the change, including changes to the pipeline itself.
2. **Every stack change goes through a PR** with `npm run verify` green. The synth step in
   CodeBuild runs the same command, so a red verify is a red pipeline.
3. **Verify prop names against `node_modules/aws-cdk-lib/**/*.d.ts`** before using them. Do not
   write CDK from memory; the L2 surface moves every release.
4. **Stateful resources are protected.** RDS (`deletionProtection`, `SNAPSHOT`), the docs
   bucket (`RETAIN`) and the user pool (`deletionProtection`, `RETAIN`) survive a stack delete.
   See "Teardown" before touching those flags.
5. `exactOptionalPropertyTypes` is switched off in `infra/tsconfig.json` only: aws-cdk-lib's
   jsii-generated interfaces do not compile under it. Do not copy that override elsewhere.

## Commands

```bash
npx tsc -b infra                      # typecheck (part of root `npm run typecheck`)
npx eslint infra --quiet              # lint
npm test -w infra                     # vitest: synthesizes the app and asserts on templates
cd infra && npx cdk synth --quiet -c hostedZoneId=Z0000000000000000TEST
cd infra && npx cdk ls                # GeDe-Pipeline + the eight GeDe-Prod-* stacks
cd infra && npx cdk diff GeDe-Pipeline --profile phani-quadnomics   # read-only, fine from a laptop
```

Docker is not needed for synth: `ContainerImage.fromAsset` only hashes the build context locally;
the image is built by the pipeline's ARM asset-publishing step.

## Where values come from

| Value                                                                            | Source                                                                                          |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Account, region, domain, alert email, budget                                     | `lib/config.ts` (`PROD`)                                                                        |
| `codeConnectionArn`, `hostedZoneId`, `appleSignIn`, `githubRepo`, `githubBranch` | `cdk.json` → `context` (override per run with `-c key=value`)                                   |
| Availability zones                                                               | `cdk.context.json` (committed, keeps synth offline) and `AVAILABILITY_ZONES` in `lib/config.ts` |
| CDK feature flags                                                                | `cdk.json` → `context` (the `recommended-feature-flags.json` set for this aws-cdk-lib)          |
| Apple credentials                                                                | Secrets Manager `gede/prod/apple-signin` (JSON: `clientId`, `teamId`, `keyId`, `privateKey`)    |
| DB credentials                                                                   | Generated by RDS into Secrets Manager; injected into the task as `PG*`                          |
| `/config.json` for the SPA                                                       | Rendered by `WebStack` from stack references at deploy time                                     |

`hostedZoneId` stays `REPLACE_AFTER_DOMAIN_REGISTRATION` until the domain exists; synth
warns but does not fail. Tests always pass a fake zone id.

The unit tests load `cdk.json` + `cdk.context.json` so they synthesize with the same flags as
the CLI. One consequence worth knowing: `@aws-cdk/core:defaultCrossStackReferences` is `weak`,
so same-region cross-stack references render as `Fn::GetStackOutput` rather than
`Fn::ImportValue`. Stack order is still enforced by CDK's dependency graph.

## Placeholders at synth time

- `services/sync/Dockerfile` missing → `assets/placeholder/sync/Dockerfile` is used and a
  warning is emitted. The placeholder image exits immediately; never deploy it.
- `apps/web/dist` missing → `assets/placeholder/web/index.html` is deployed and a warning is
  emitted. Build the web app first (`npm run build --workspace apps/web`); the pipeline does.

## Design decisions to keep

- **No NAT gateway.** Fargate runs in the public subnets with a public IP and a security group
  that admits only the ALB. RDS is in isolated subnets and admits only the service SG. S3 goes
  through the gateway endpoint. Adding NAT is ≈ US$35/mo per AZ for nothing at this scale.
- **DB ingress lives in ServiceStack** (`addIngressRule(..., remoteRule = true)`), so DataStack
  never depends on ServiceStack and stateful stacks deploy first.
- **Passwordless Cognito.** Cognito requires PASSWORD in `AllowedFirstAuthFactors` of a
  choice-based pool (CloudFormation rejected the override on 2026-09-12), so the pool policy is
  `[PASSWORD, EMAIL_OTP, WEB_AUTHN]`. Passwordless is enforced at the client: the SPA app client
  has only `authFlows: { user: true }` and the web app never renders a password field (root rule 6).
  Do not add `userPassword`/`userSrp` flows to the client.
- **Cognito sends its own mail** until SES leaves the sandbox; the `withSES` block in
  `AuthStack` is ready to swap in (the SES identity and DKIM records already exist).
- **CloudFront `/api/*` reaches the ALB by hostname** (`api.<domain>`), not by construct
  reference, so WebStack does not depend on ServiceStack and the two deploy in parallel.
- **AAAA records only for CloudFront.** The VPC has no IPv6 block, so the ALB is IPv4-only.
- **`GeDe-Pipeline-support-us-east-1`** is generated by CodePipeline for the us-east-1 Edge
  stack (artifact replication bucket). It is not one of ours; leave it alone.
- A `CloudFormation-Validate::W7001` warning about an unreferenced
  `AWSCloudFrontPartitionHostedZoneIdMap` mapping in `GeDe-Prod-Web` is CDK-internal
  (`CloudFrontTarget` copies the mapping into `Dns`). Harmless.

## Playwright on CodeBuild

The Synth step runs `npm run e2e` between `npm run verify` and the web build, on the same
`aws/codebuild/amazonlinux-aarch64-standard:3.0` (AL2023, arm64, `SMALL`) project. A red
journey fails Synth, so nothing is published or deployed. Why this and not a Playwright
Docker image (`mcr.microsoft.com/playwright:v<ver>-noble` via
`LinuxArmBuildImage.fromDockerRegistry`):

- **The arm64 Chromium binaries run on AL2023.** Playwright 1.63 pins Chrome for Testing
  153.0.8010.12; its `chrome-headless-shell-linux-arm64` binary imports `GLIBC_2.17/2.18/2.25`
  only and its `deb.deps` asks for `libc6 >= 2.25` and `libnss3 >= 3.35`. AL2023 ships glibc
  2.34 and nss 3.112 (checked in the AL2023 aarch64 core repo metadata, 2026-09-12).
- **`npx playwright install --with-deps` cannot work on AL2023.** `installDependenciesLinux`
  in `playwright-core` always runs `apt-get`; AL2023 (`ID=amzn`) is not a distro Playwright
  recognises, so it falls back to the `ubuntu24.04-arm64` package list with a warning. The
  pipeline therefore installs the dnf equivalents itself (`CHROMIUM_DNF_PACKAGES` in
  `lib/pipeline-stack.ts`, one per Debian package in Playwright's list; every name verified
  against the repo) and then `npx playwright install --only-shell chromium`.
- **One less image to trust and pull.** A pulled image would add a registry dependency to
  every deploy and a second CodeBuild project; the dnf step is ~20 packages from the AL2023
  mirror the build already uses.
- **Cost.** ~2–3 min on `SMALL`: dnf ≈ 40 s, headless shell download ≈ 95 MB (cached in
  `/root/.cache/ms-playwright` by the local custom cache when the host is reused), e2e build
  ≈ 15 s, journeys ≈ 30–60 s with two workers.

Fallback if the dnf approach ever breaks (for example CfT starts requiring a newer glibc):
move `npm run e2e` into a dedicated `pipelines.CodeBuildStep` whose `buildEnvironment` is
`codebuild.LinuxArmBuildImage.fromDockerRegistry('mcr.microsoft.com/playwright:v<ver>-noble')`
and add it as a `pre` step of the Prod stage. Keep `CI=true` in `env` either way.

`docs/TESTING.md` explains the suite itself.

## Switches

**Staging + manual approval.** In `lib/pipeline-stack.ts`, add a second `GedeStage` with a
`STAGING` config (new `EnvConfig` in `lib/config.ts`, its own domain or subdomain and hosted
zone) and `pipeline.addStage(staging)` before `prod`; then uncomment
`pre: [new pipelines.ManualApprovalStep('PromoteToProd')]` on the Prod stage. Stack names
follow `GeDe-<EnvName>-<Stack>` automatically.

**Sign in with Apple.** Create the `gede/prod/apple-signin` secret, set `appleSignIn: true`
in `cdk.json`, merge. `AuthStack` adds the Apple IdP, the hosted-UI domain `gede-prod`, and
the OAuth callback `https://gede.work/auth/callback`; `/config.json` flips `appleSignIn`.

**SES production mail.** After production access is granted in ap-southeast-1, replace
`UserPoolEmail.withCognito()` with the commented `withSES` block.

## Teardown (only if you really mean it)

1. Set `deletionProtection: false` on the RDS instance and the user pool, and change
   `removalPolicy` to `DESTROY` where you accept data loss (RDS, docs bucket, user pool).
   Merge and let the pipeline apply it — the flags must be deployed before a delete works.
2. `cdk destroy` the stage stacks in reverse order (Dns, Ops, Web, Service, Data, Auth, Edge,
   Network), then `GeDe-Pipeline` and `GeDe-Pipeline-support-us-east-1`.
3. Anything with `RETAIN` (docs bucket, user pool) must then be deleted by hand.
