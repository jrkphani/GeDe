# GeDe runbook

Operations for the production environment. Commands assume the AWS CLI with a profile that can assume an administrator role in account 975049998516 (`--profile phani-quadnomics` locally) and `--region ap-southeast-1` unless stated. Stack names are `GeDe-Prod-<Network|Data|Auth|Edge|Service|Web|Dns|Ops>`; the Edge stack lives in `us-east-1`. Physical names of the ECS cluster, service, log group and secrets are generated by CDK, so the commands below discover them by prefix.

## 1. How a deploy happens

Merging to `main` is the deploy. There is no other path.

1. GitHub notifies CodePipeline `GeDe` through the CodeConnections connection (`triggerOnPush`).
2. Synth runs `npm ci`, `npm run verify`, `npm run audit` (production dependencies, high+ advisories fail), `npm run db:parity -w packages/db`, `npm run e2e`, `npm run build --workspace apps/web`, `npm run synth --workspace infra` on CodeBuild ARM (`AMAZON_LINUX_2023_STANDARD_3_0`, SMALL, `node_modules` and the Playwright cache kept locally). Every CodeBuild project logs to one group with 30-day retention.
3. SelfMutate updates the pipeline if `infra/lib/pipeline-stack.ts` changed the pipeline itself, then restarts the execution.
4. Assets builds the `linux/arm64` sync image from the repo root with `services/sync/Dockerfile` and publishes assets to both regions.
5. Prod deploys the eight stacks (Edge in `us-east-1`, the rest in `ap-southeast-1`; Web before Service, see ADR-018). ECS performs a rolling replacement of the sync task with the deployment circuit breaker on.
6. Smoke curls `$APP_URL/api/health` through CloudFront (12 retries, 10 s apart), checks `$APP_URL/` for `id="root"`, and asserts that `$API_URL/api/health` — the bare ALB hostname, without the origin-verify header — answers 403. All URLs are stage outputs.
7. Playwright-Live signs in to `https://gede.work` as `e2e@gede.work` (through the `gede-e2e` client and the `gede/prod/e2e-user` secret) and runs `apps/web/e2e-live/` — library, new workscape, a cell edit that survives a reload and a fresh browser, find, the share sheet, Delete All, sign out (docs/TESTING.md "Live suite"). Same image as Synth, its own role `gede-pipeline-playwright-live`, about 3 minutes.

Expect 15–25 minutes from merge to Smoke green and a few more to Playwright-Live. RDS and Cognito changes take longer.

## 2. Rollback

Automatic:

- A task that fails its health check trips the ECS circuit breaker; the service rolls back to the previous task definition and the CloudFormation update fails and reverts.
- A CloudFormation error in any stack rolls that stack back; the pipeline stops before Smoke.
- A Smoke failure marks the execution failed. The infrastructure is already updated at that point; the previous task set is gone. Treat Smoke red as an incident: check `/healthz` and the service logs, then roll forward or revert.
- A Playwright-Live failure is the same kind of red: production is already deployed and **nothing rolls back**. Open the step's log (`aws logs tail /aws/codebuild/<PlaywrightLive project>`), read which step of the journey failed and the Playwright trace it names, then decide: a product defect → revert the merge; a suite defect (a renamed control, a flaky wait) → fix the suite and merge. A pipeline that ends red on Playwright-Live still deployed the commit.

Forced:

1. Fastest and preferred: revert the merge commit on `main` (`git revert <sha>`, PR, merge). The pipeline redeploys the previous code with a new execution and `main` stays truthful.
2. Re-run a previous execution: console → Pipelines → GeDe → the last green execution → Retry, or `aws codepipeline start-pipeline-execution --name GeDe --source-revisions actionName=Source,revisionType=COMMIT_ID,revisionValue=<sha>`. This deploys that commit but leaves `main` ahead of production; follow with a revert.
3. Database: migrations are forward-only. If a migration must be undone, write the reverse migration and deploy it. Use RDS point-in-time restore only for data loss, never for schema. The ledger stores a checksum per applied file: a task that boots with an edited shipped migration exits with `migration <file> failed: file text differs`, the circuit breaker keeps the previous task set, and the fix is to restore the file's text and add the change as a new migration.

**Rotate the app password.** The bootstrap step runs `ALTER ROLE gede_app PASSWORD …` from `PGAPPPASSWORD` on every boot, so rotation is: write a new password into the secret, then start new tasks. A task that boots with the new secret re-applies the role before its runtime pool connects, so a new task never has the wrong password. The old task is the one with a window: PostgreSQL checks the password at connect time only, so its open connections keep working, but its pool opens fresh connections whenever one has sat idle for 10 s (`pg`'s default `idleTimeoutMillis`) or the pool grows, and from the moment the new task's bootstrap commits until the old task is drained those connects fail with `password authentication failed`. Expect some `/api` 500s and WebSocket joins failing on the old task for the length of the rolling deployment (health check plus ALB deregistration delay); document updates already written are safe, every update is in `doc_updates` before it is fanned out. Do the two commands below back to back for the same reason: a nightly jobs task (§14, 02:30 Asia/Singapore) that starts between `put-secret-value` and the redeploy rotates the role under the running service, which then cannot reconnect until it is redeployed.

```bash
NEW=$(aws secretsmanager get-random-password --password-length 48 --exclude-punctuation --query RandomPassword --output text)
aws secretsmanager put-secret-value --secret-id gede/prod/db-app \
  --secret-string "{\"username\":\"gede_app\",\"password\":\"$NEW\"}"
aws ecs update-service --cluster "$CLUSTER" --service "$SERVICE" --force-new-deployment
# The nightly jobs task reads the secret on its next start; run it by hand (§14) to confirm.
```

If a task logs `database app role misconfigured; exiting`, the secret injection failed (missing key, secret deleted): the task refuses to boot rather than run as the master user. Restore the secret's `username`/`password` keys and redeploy. If it logs `migration app role bootstrap failed`, read the cause in the same line — the master user could not create or alter the role (an RDS parameter, or a role of that name owned by someone else).

## 4. Enable Sign in with Apple

Prerequisites: an Apple Developer team, an App ID, a Services ID whose return URL is `https://<cognito-domain>/oauth2/idpresponse`, and a Sign in with Apple key (`.p8`).

1. Create the secret: `aws secretsmanager create-secret --name gede/prod/apple-signin --secret-string file://apple.json` with the four fields above.
2. In `infra/cdk.json` set `"appleSignIn": true`. Commit and merge. The Auth stack adds the Apple identity provider to the pool and the client; the Web stack writes `"appleSignIn": { "domain": "gede-prod.auth.ap-southeast-1.amazoncognito.com" }` into `config.json` (`false` while the flag is off; the SPA rejects any other shape at boot, #61).
3. The SPA renders Apple's button (black, Apple's glyph, 44 pt, below the passkey button) only when `config.json` says so.
4. Verify on `https://gede.work`: Sign in with Apple federates into the same `users` row by verified email (AUTH-08).

To disable, set the flag back to `false` and merge; the secret can stay.

## 5. Enable SES sending

Cognito sends one-time codes with its built-in sender (50 per day) until SES has production access.

1. Request production access in `ap-southeast-1`: `aws sesv2 put-account-details --production-access-enabled --mail-type TRANSACTIONAL --website-url https://gede.work --use-case-description "..."`. Wait for the approval email.
2. The Auth stack already creates the SES `EmailIdentity` for `gede.work` with DKIM records in Route 53. Confirm `aws sesv2 get-email-identity --email-identity gede.work` shows `VerifiedForSendingStatus: true`.
3. In `infra/lib/stacks/auth-stack.ts` replace `email: cognito.UserPoolEmail.withCognito()` with the `withSES({ fromEmail, fromName, sesVerifiedDomain, sesRegion })` block that sits commented directly beneath it. Merge.
4. Share invitations from the sync service use SES from the start; in sandbox they only reach verified addresses.

## 6. Add a Staging stage

1. In `infra/lib/config.ts` add a `STAGING` constant (`envName: 'staging'`, `domain: 'staging.gede.work'`, same account and region, its own budget).
2. In `infra/lib/pipeline-stack.ts`, before `Prod`, add `const staging = new GedeStage(this, 'Staging', { env, config: STAGING, hostedZoneId, appleSignIn: false })` and `pipeline.addStage(staging)`.
3. Uncomment `pre: [new pipelines.ManualApprovalStep('PromoteToProd')]` on the Prod stage.
4. The Dns stack derives `api.`, `ws.` and `www.` from `config.domain`, so `staging.gede.work` needs a delegated hosted zone or the Dns stack taught to write into the apex zone with a deeper record name. Passkeys registered on `gede.work` do not work on the staging host.
5. Merge. SelfMutate adds the stage; the next execution deploys Staging, pauses for approval, then Prod. Cost roughly doubles (second ALB, RDS, task, WAF).

## 7. Rotate the RDS CA bundle

The task connects with `PGSSLMODE=verify-full` and `PGSSLROOTCERT=/app/rds-global-bundle.pem`; the Dockerfile copies that file from `infra/lib/rds-global-bundle.pem`.

1. Download the current bundle: `curl -o infra/lib/rds-global-bundle.pem https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem`.
2. Check the instance's CA: `aws rds describe-db-instances --query 'DBInstances[0].{id:DBInstanceIdentifier,ca:CACertificateIdentifier}'`. If AWS has scheduled a CA change, after the bundle is deployed run `aws rds modify-db-instance --db-instance-identifier <id> --ca-certificate-identifier rds-ca-rsa2048-g1 --apply-immediately`.
3. Commit the bundle, merge, watch the pipeline. The task reconnects with the new bundle on deploy.

## 9. Cost expectations

About US$62 per month: ALB ≈ 18, Fargate ARM ≈ 15, RDS `db.t4g.micro` ≈ 15, WAF ≈ 6, CloudFront + S3 + Route 53 ≈ 3, CloudWatch ≈ 3, CodeBuild ≈ 2. Domain US$14 per year. A NAT gateway would add ≈ 33. A Staging stage roughly doubles the compute lines. The nightly purge task (0.5 vCPU / 1 GiB ARM for about a minute a night), its schedule, the EventBridge rule and the extra alarm together add well under US$1 per month. Because the image now carries the git sha as a build arg, every merge builds and publishes a new image (≈ 100 MB in ECR per deploy; the ECR lifecycle keeps the last few) — a few cents a month.

## 12. Rotate the origin-verify header

The value CloudFront sends the ALB in `X-Origin-Verify` (ADR-018) is rotated by generation, never by editing a secret value. Three merges, zero downtime. Web deploys before Service, so CloudFront must never be moved to a generation in the same merge that adds it: for the whole Service deploy the ALB would still refuse the new value.

1. In `infra/lib/stacks/web-stack.ts` change `ORIGIN_VERIFY_GENERATIONS` from `[N]` to `[N, N+1]`; leave `ORIGIN_VERIFY_PRESENTED` at `N`. Merge. The Web stack creates the new secret (CloudFront still presents N) and the ALB rule accepts both.
2. Once Smoke is green, change `ORIGIN_VERIFY_PRESENTED` to `N+1`. Merge. CloudFront moves to the new value; the ALB already accepts it.
3. Once Smoke is green, change `ORIGIN_VERIFY_GENERATIONS` to `[N+1]`. Merge. The old secret is deleted (Secrets Manager keeps it recoverable for the default window) and the ALB rule drops the old value.

Synth refuses a `ORIGIN_VERIFY_PRESENTED` that is not in `ORIGIN_VERIFY_GENERATIONS`, so steps cannot be merged out of order.

Do this immediately if a CloudFront origin configuration or a Secrets Manager read was exposed. Do not put a value into a secret by hand: CloudFormation only re-resolves the `{{resolve:secretsmanager:…}}` references when it updates the listener rule and the distribution, so a hand-edited value would silently break `/api/*` at the next unrelated deploy of either stack.

## 14. Nightly purge (LIB-08)

Recently Deleted holds a document for 30 days. Past that, the document is no longer recoverable from the library, and the nightly job removes it for good: the `documents` row (which cascades to `doc_updates`, `snapshots`, `shares`, `invites`), a `document.purge` row in `audit_log` with `user_id` null (the system actor; Delete All writes the owner's id), then the S3 objects under `docs/<docId>/`. The projection rows cascade with the document.

How it runs: EventBridge Scheduler `gede-prod-nightly-purge` (02:30 Asia/Singapore, one retry within the hour) starts the `gede-prod-jobs` Fargate task definition — the same image as the service with command `node main.js --job purge` — on the service cluster, in the public subnets with a public IP and the service security group. The task applies migrations under the advisory lock (a no-op after the service has booted), purges in batches of 100, and exits 0. It exits 1 when any S3 prefix could not be removed (the rows are already gone) or the database failed; that fires the `gede-prod-purge-task-failed` rule (email with task ARN, stop code, reason) and, from the log line, the `gede-prod-purge-failed` alarm.

```bash
# Schedule state and last run
aws scheduler get-schedule --name gede-prod-nightly-purge --query '{state:State,expr:ScheduleExpression,tz:ScheduleExpressionTimezone}'
JOBS_LOG=$(aws logs describe-log-groups --log-group-name-prefix GeDe-Prod-Service-JobsLogs --query 'logGroups[0].logGroupName' --output text)
aws logs tail "$JOBS_LOG" --since 24h            # look for "purge complete" and the counts

# Run it now (same task, same command), e.g. after fixing a failure
CLUSTER=$(aws ecs list-clusters --query "clusterArns[?contains(@, 'GeDe-Prod-Service')]|[0]" --output text)
TASKDEF=$(aws ecs list-task-definitions --family-prefix gede-prod-jobs --sort DESC --max-items 1 --query 'taskDefinitionArns[0]' --output text)
SERVICE=$(aws ecs list-services --cluster "$CLUSTER" --query 'serviceArns[0]' --output text)
NET=$(aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" --query 'services[0].networkConfiguration' --output json)
aws ecs run-task --cluster "$CLUSTER" --task-definition "$TASKDEF" --launch-type FARGATE --network-configuration "$NET"

# Rebuild the search projection for one document, or all live documents
aws ecs run-task --cluster "$CLUSTER" --task-definition "$TASKDEF" --launch-type FARGATE --network-configuration "$NET" \
  --overrides '{"containerOverrides":[{"name":"purge","command":["node","main.js","--job","reproject","all"]}]}'
```

Order of operations, per batch of 50: the rows are claimed (`FOR UPDATE SKIP LOCKED`), each document's S3 prefix is removed while the claim is held, and only the documents whose objects went are deleted when the transaction commits. When the job reports `snapshot objects not removed; the document is kept for the next run` (and exits 1 with `purge could not remove every document`), nothing is orphaned: the document's rows and objects are both still there and the next night retries them. Fix the S3 error (permissions, throttling) and either wait for the schedule or run the task by hand. The bucket is versioned, so a removal writes delete markers; the lifecycle rule expires the noncurrent versions and the markers after 90 days.

What the purge never touches: live documents, documents deleted less than 30 days ago (measured on the database clock, `deleted_at < now() - 30 days`), and `audit_log`.
