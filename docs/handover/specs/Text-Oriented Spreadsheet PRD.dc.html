Product Requirements Document: GeDe — Text-Oriented Spreadsheet

Specification · sections 1–24 · v1 scope

1. System Architecture & Data Model

  • State Engine: Directed Acyclic Graph (DAG) replacing the traditional 2D grid. Each cell is a node; string operations are edges ensuring downstream updates flow dynamically when parent data changes.
  • Frontend Stack: React and TypeScript to handle complex localized state management, DOM manipulation, and rich text rendering.
  • Data Structure: Cells store values as rich-text JSON objects (similar to Quill Deltas or Slate.js nodes) rather than plain string primitives. This ensures formatting is preserved during text transformations.
  • AI Translation Layer: API integration with enterprise LLM endpoints (e.g., Amazon Bedrock) to translate natural language intents into executable Regex and classification rules.removed in v1

2. User Interface & IDE-Style Autocomplete

The core interaction model abstracts spreadsheet formulas into an object-oriented, dot-notation interface.

Interaction System Behavior Example
Entity Reference Typing @ triggers an autocomplete dropdown of available columns or specific parent cells. @RawNotes
Action Menu Typing . after a reference cascades a hierarchical menu of available string methods. @RawNotes.Extract
Property Panel Selecting a method opens an inline declarative UI widget to define arguments without writing syntax. User selects .Replace(), panel requests "Target" and "Replacement" values.

3. Rich Text & Styling Engine

Text functions simultaneously as manipulatable data and a visual presentation layer.

  • Inline Formatting: Support for bold, italic, underline, strikethrough, superscript, and subscript.
  • Color & Typography: Font family selections, font size, text color (hex/RGB), and highlight/background colors.
  • Semantic Presets: One-click application of structural styles to standardize outputs:
    • Title: Primary header scale and weight.
    • Heading: Secondary sectioning scale.
    • Body: Default standard text scale.
  • Format-Aware Operations: Formatting can be utilized as query logic (e.g., @Column.Extract(Style="Highlight:Yellow") to pull only highlighted terms into a new column).

4. Hierarchical Data Structures

The UI must visually represent the lineage of how text is broken down or combined.

  • Nested Row Hierarchies: When a cell is divided (e.g., applying @Paragraph.Split(". ")), the resulting array of strings renders as collapsible child rows nested beneath the parent cell.
  • Column Lineage (Pipelines): Derived columns are grouped visually under their parent column. If Column C (Format to Title Case) modifies Column B (Extracted Names), which derives from Column A (Raw Data), they share a horizontal audit trail structure rather than existing as independent silos.

5. Abstracted Pattern Matching

  • Smart Chips: Pre-built, drag-and-drop Regex rules for standard corporate data types (e.g., 📧 Email, 📅 Date, 💵 Currency, 🏢 Company Entity).
  • Flash Fill (Inference): The system generates extraction rules automatically based on output examples provided by the user in adjacent columns.
  • Natural Language to Regex: A GenAI text box allowing users to state their intent (e.g., "Pull out the text inside the parentheses") which silently compiles and executes the underlying Regex.removed in v1

To support an infinite, zoomable workspace with granular visual controls, the application must move beyond standard DOM layouts and utilize a spatial rendering architecture.

6. Canvas & Rendering Engine

  • Infinite Virtual Workspace: The application operates on a coordinate-based infinite plane (similar to Figma or Miro) rather than a fixed-dimension page.
  • Viewport Virtualization: To maintain 60fps performance across thousands of text nodes, the rendering engine (utilizing HTML5 Canvas or WebGL via libraries like PixiJS or React Flow) must employ spatial hashing or quadtrees. Only cells currently visible within the user's viewport are rendered to the DOM or Canvas.
  • Semantic Zooming:
    • Micro-level (Zoomed In): Displays full rich-text formatting, inline styling, and cell-level action menus.
    • Macro-level (Zoomed Out): Text scales down cleanly; at extreme zoom-outs, individual cell text fades out, and parent-level block titles, data pipelines, and hierarchical table structures become the primary visual indicators.

7. Grid & Border Logic

Because text data is often free-flowing, the rigid visual structure of a standard spreadsheet is decoupled from the data relationships and made entirely customizable.

Element Visibility Logic Styling Implementation
Global Gridlines Contextual / On-Demand Rendered as a lightweight background pattern on the canvas layer. Can be toggled globally (Off, Light, High Contrast) or set to appear only when a user is actively dragging/resizing a table.
Table Boundaries Explicit / Object-Level Tables function as independent containers floating on the infinite canvas. Users can apply explicit CSS-equivalent stroke borders (solid, dashed, weight, color) to mark the perimeter of a dataset.
Cell Borders Inherited / Custom Individual cells or row hierarchies within a table can override the parent table's border properties to visually separate parent data from extracted child outputs.
Connecting Edges Algorithmic Since the system uses a DAG state, visual bezier curves or orthogonal lines can be toggled on to show the flow of string operations from a parent table to a derived child table across the canvas.

Here are the additions to the specification document, adapting these spreadsheet mechanics specifically for text manipulation and an infinite canvas architecture.

8. Conditional Formatting (Semantic & Pattern Highlighting)

This system evaluates string logic to dynamically apply rich-text and cell-level styling, providing visual cues for data quality and categorization.

  • Logic Triggers:
    • Lexical: String contains/does not contain specific substrings or keywords.
    • Metrics: String length exceeds or falls below character/word count thresholds.
    • Pattern-Based: String matches or fails to match a Smart Chip (e.g., flagging rows red if they fail an "Is Valid Email" regex check).
    • Semantic (AI-driven): Triggering styles based on intent or sentiment (e.g., highlighting negative customer feedback).removed in v1
  • Style Outputs: Dynamically overrides cell background color, borders, or applies rich text presets (e.g., automatically applying a strikethrough and gray text to rows flagged as "Archived").

9. Advanced Filtering & Lexical Sorting

Sorting and filtering must handle unstructured text properties beyond traditional alphabetical or numerical order.

  • Lexical Sorting Modes:
    • Standard A-Z / Z-A.
    • By Volume: Sorting by character count or total word count (e.g., bringing the longest paragraphs to the top).
    • By Frequency: Sorting strings based on how often they appear in the dataset.
  • Semantic Filtering:
    • Faceted Filtering: Filtering rows to display only strings that contain specific extracted entities (e.g., show only rows where @Row.Extract.Date() is present).
    • Fuzzy Filtering: Returning results that closely match a query, accounting for typos or variations (e.g., filtering for "Singapore" also returns "Sngapore").

10. Viewport Anchoring (Freeze Panes)

Because the application utilizes an infinite spatial canvas rather than a fixed grid, "freezing" is treated as pinning elements to the user's viewport.

  • Node Pinning: Users can select any table, column, or specific parent cell and toggle "Pin to Viewport."
  • Behavior on Pan/Zoom: Pinned elements detach from the canvas coordinate system and anchor to the edge of the screen (similar to a sticky header or floating widget). This allows users to keep master parent data visible while panning horizontally or vertically across the canvas to inspect derived child pipelines and transformations.
  • Ghosting: When an element is pinned, a semi-transparent "ghost" outline remains in its original spatial position on the canvas to maintain context of where it belongs in the overall Directed Acyclic Graph (DAG) flow.

11. Workbook & Sheet Model

A document is a workbook of sheets, each sheet an independent infinite canvas holding any number of tables.

  • Sheet Tabs: A persistent tab strip below the toolbar lists every sheet with its ordinal, name, and table count. Selecting a tab swaps the canvas contents and resets the viewport to the sheet's origin. A trailing + appends a new empty sheet at the end of the strip.
  • Empty Sheets: A sheet with no tables still presents its coordinate plane, with an explicit affordance to place the first table.
  • Child Sheets: Opening a graph context creates a sheet named after its symbol, holding a shaped table for that context's children (Section 19).
  • Cross-Sheet Lineage: DAG edges whose endpoints live on different sheets are reported numerically in the inspector rather than drawn, so the audit trail survives the sheet boundary.

12. Coordinate Grid & Cell Addressing

The infinite canvas is itself the cell grid. Spatial position and spreadsheet address are the same fact expressed two ways.

  • Lattice: A uniform lattice of fixed column width and row height underlies the plane. Cell A1 is the top-left origin; the canvas extends right and down from it and cannot be panned above or left of that origin.
  • Rulers: Column letters run along the top edge and row numbers down the left, rendered in canvas space so they track pan and zoom exactly. Each table's column headers additionally display their grid letter.
  • Snapping: Table origins, column widths, and row heights snap to whole lattice units. A table is therefore always addressable, and resizing never desynchronises the ruler from the data.
  • Frozen Header Columns: A per-table count declares how many leading columns are frozen. Frozen columns are shaded, separated from the body by a heavier rule at the freeze boundary, and are the columns carried into the pinned-viewport panel described in Section 10.
  • Address Resolution: Every cell carries a computed A1 address, surfaced in the formatting bar alongside its column name. Addresses recompute when rows or columns are inserted, deleted, hidden, or when wrapped rows occupy two lattice rows.

13. Formula Layer

Typing = in a cell opens formula entry, offering a menu of available forms. References may be spatial or semantic, and the two are interchangeable within one expression.

Form Behavior
=Concat(a, b, …) Joins arguments end to end. Each argument may be a cell address, an @ entity path, or a quoted literal.
=A2, D5 Lists the values at the given grid addresses, comma separated.
=Sum(B2:B14) Adds the numeric values in a range, list of addresses, or @ paths. Available only when the referenced cells carry a Number or Currency format (§22); text-formatted cells make the formula an error, not a silent zero.
=@Group.Entity, @Group.Entity Resolves entity paths anywhere in the workbook, separated by whatever literal text is typed between them.
  • Entity Autocomplete: Typing @ inside a formula opens a dropdown of every addressable entity in the workbook, expressed as a dotted path qualified by its parent row. Selecting an entry inserts the path at the cursor and leaves the editor open for further arguments.
  • Live Evaluation: Formula results track their sources. Editing a referenced cell updates every dependent expression, and formulas may reference other formulas; a depth guard reports circular references.
  • Presentation: A formula cell renders its resolved value with a reference badge and shows the expression on a secondary line. Re-opening the cell for editing restores the expression, not the result.
  • Reference Highlighting: While a formula cell is selected or being edited, every cell it reads is outlined on the canvas in the colour of its position in the expression (first reference, second reference …), and ranges are drawn as one outlined block. The outlines follow pan and zoom and clear on deselect.

14. Cross-Table Relationships

  • Row Pulls: A table can mirror rows from any table on any sheet, filtered by a contains-expression. The receiving column renames itself to name its source, and mirrored values stay live.
  • Mapping Columns: A column can be bound to a target column elsewhere in the workbook; its cells then present one-click pickers over that column's distinct values, producing a governed many-to-one mapping.
  • Reference Cells: Any cell may be turned into a direct reference to another table's cell through the @ entity index, without a formula.

15. Row Grouping (Categories)

  • Group by Column: Rows sharing a value in a chosen column collapse into category bands. Each band states the value and its row count on the grouped column and can be collapsed.
  • Interaction with Sort and Filter: Grouping applies after sorting and filtering, so the active order and predicate are preserved within each band.
  • Manual Hierarchy: Independently of categories, any row can be promoted or nested one level relative to the row above it, forming the parent-child outline described in Section 4.

16. Direct Manipulation & Keyboard Model

  • Selection and Editing: A single click arms a cell; a double click or Enter opens it for editing; typing any character begins overwriting. Escape cancels, Delete clears.
  • Traversal: Tab and the arrow keys move the selection, wrapping at row ends. Tabbing or arrowing past the final row appends a new row and places the cursor in it.
  • Shortcuts: Modifier combinations apply inline formatting and adjust hierarchy depth without leaving the keyboard.
  • Structural Affordances: An add-row strip sits beneath the last row of the selected table and an add-column stub at its right edge, each occupying exactly one lattice unit.
  • Resizing: Column dividers resize individual columns; a corner handle scales the whole table. Both snap to the lattice.

17. Contextual Menus

Right-clicking a column header or a cell opens a context menu following desktop spreadsheet conventions, with checkmarked toggles, separated groups, and unavailable commands shown disabled rather than hidden.

  • Column Header: Freeze header columns; sort ascending, descending, and sort options; quick filter and filter options; add, remove, and configure a category for the column; add column before or after; delete; hide; fit width to content; the clipboard group; wrap text.
  • Cell: Freeze header rows and columns; add row above or below; add column before or after; delete row or column; sort, filter, and category options; merge controls; cut, copy, copy snapshot, paste, paste and match style, clear all; wrap text.

18. Inspector Panels

A collapsible right-hand inspector holds two modes, selected from the window chrome. A window chrome bar above the canvas carries the document identity, grouped tool clusters with icon affordances and tooltips, zoom with fit-to-canvas, and the inspector toggles. Toolbar and inspector controls are not duplicated: each command has exactly one home, and any control whose effect is not implemented is rendered disabled rather than styled as operable.

  • Format — Table: Table styles; title and caption visibility; header row, header column, and footer row counts, each of which adds or removes the corresponding band; row and column counts that insert or delete structure; table outline; gridline density; alternating row colour; and row and column sizing with fit-to-content.
  • Format — Cell: Data format, fill, and a positional border matrix — all edges, any single edge, outline, paired edges, or none — carrying a hairline, strong, or accent weight. Conditional highlighting rules are evaluated against cell text.
  • Format — Text: Font family; a four-step weight scale; size; inline marks; semantic character styles; text colour; horizontal and vertical alignment; and text wrapping.
  • Format — Arrange: Stacking order, canvas layout alignment, size, and position reported both in pixels and as a grid address, plus viewport pinning and DAG edge visibility.
  • Format — Derive: The application's own apparatus — cross-table relation, derived-column composition, hierarchy controls, and the pipeline audit list.
  • Organize: Categories, Sort, and Filter, each with an enable toggle, an add-control, and the lexical and semantic modes defined in Section 9.

19. Graphs — the N-Dimensional Context Matrix

A graph renders a table as an N-dimensional matrix: chosen columns are the dimensions, each column's distinct values are that dimension's parameters, and each row is a context — one coordinate per dimension. The graph is a read-only view of the table; all authoring happens in cells. This replaces a separate compose ritual with the row.

  • Adding a Graph: From the chrome toolbar (+ Graph beside + Table), from a table's context menu (Graph this table), or from the empty-sheet menu (Table / Shaped table / Graph). Every add produces a linked pair — a ring and a coverage grid — placed side by side below the sheet's tables. The pair shares its table, dimensions, and slice; position and size are per object.
  • Pointing: An unbound graph enters pointing mode: every table on the canvas takes a dashed accent outline, a banner states the instruction, and clicking a table binds the pair. Esc cancels. Alternatively Add shaped table creates a pre-shaped table (Dimension A · B · C · Notes) and binds it in one step.
  • Binding Panel: Selecting a graph adds a Graph tab to the inspector: the source table with Re-point; a checklist of source columns to mark as dimensions, each showing its distinct-value count; Add dimension column; coverage axis chips and pinned values; the context count; Remove graph. Derived, linked, and pulled columns are not offered — a context must be typeable back into its table.
  • Live Derivation: Dimensions, parameters, and contexts are recomputed from the table on every change. Symbols (α β γ …) are generated by row order. A row bound on every dimension is complete and renders as a filled node; a partially bound row is a draft and renders hollow and dashed. There is no separate documented state.
  • Ring: One arc per dimension, coloured from a fixed palette, with a dot per parameter. Contexts sit on concentric orbits inside the arcs (1, 6, 12, 18 …) so large tables stay legible. The header states distinct covered tuples over the total tuple space.
  • Coverage: One 2-D slice of the matrix — rows and columns are two dimensions chosen by chips, every remaining dimension is pinned to a value. Pinned values default to the selected context's bindings so the slice shown contains the selection. Filled cells carry the context symbol.
  • Emphasis: Hovering a node, dot, or coverage cell mutes everything not adjacent across the whole pair and draws spokes from the context to its parameters; selection dims softly. Hover also lights the source row in the table.
  • Write-back: Clicking a node selects its row in the source table. Clicking an empty coverage cell appends a row pre-filled with that tuple. Double-clicking a node opens a new sheet named after the symbol, containing a shaped child table.
  • Geometry: Graphs are canvas objects on the lattice: drag the header to move, the corner handle to resize, both snapping to grid units. The ring scales to fit its box; the default size is roomy (6 × 28 units). Fit-to-canvas frames tables and graphs together.

20. Technical Architecture Review

Each stack choice in Sections 1 and 6 is tested against what Sections 11–19 actually demand. Verdicts: keep, narrow (keep with a constraint), or change.

ChoiceStress testVerdict and recommendation
DAG state engine
§1
Correct model, but under-specified. Formulas (§13), references, pulls (§14), derived columns, grouping and graphs (§19) all read the same cells; a naive DAG re-evaluates whole tables per keystroke. Cycles are user-reachable (=A1 in A1), and address-based references (§12) re-key when rows are inserted, so edges cannot be stored by address.narrow Keep the DAG, specify it as an incremental reactive graph: nodes keyed by stable cell ids (never by A1 address), pull-based lazy evaluation with dirty marking, topological batching per input event, and an explicit cycle detector surfacing ⚠ circular. Candidates: a signals library (Preact Signals, Jotai) or a purpose-built engine in the style of HyperFormula’s dependency graph. Address-to-id resolution is a separate index rebuilt on structural edits.
React + TypeScript
§1
Adequate for chrome, inspector, menus. Stress point is the canvas: React reconciliation per cell across thousands of nodes at 60 fps is the known failure mode, and the prototype already renders every cell through the component tree.keep Keep for everything outside the grid body. Render the grid body through a virtualised layer (only rows and columns intersecting the viewport, plus one margin) with memoised row components keyed by cell id. Formula evaluation runs outside React and pushes only changed cell values.
Rich-text JSON (Quill Deltas / Slate nodes)
§1
Format-aware operations (§3, Extract(Style="Highlight")) need spans with attributes that survive Split, Replace, Extract, Concat. Quill Deltas serialise well but have no schema; Slate’s data model changes between versions and its editor is heavy for a cell. Neither defines how a mark maps through a substring operation.change Adopt a ProseMirror-family schema (ProseMirror or Tiptap) for the document model: typed marks, a stable transform algebra, and a mature contenteditable for in-cell editing. Specify a small text-transform library operating on marked strings that preserves marks through slicing and concatenation; every formula method in §13 is defined on this type, not on plain strings.
Amazon Bedrock for NL → regex
§1, §5
Latency of hundreds of milliseconds per request; non-determinism between calls; hallucinated patterns; and user text reaching a regex engine, where catastrophic backtracking is a denial-of-service vector.removed Removed from v1 along with the natural-language feature (§21). Smart Chips remain and ship as pre-validated RE2-compatible patterns executed in a Web Worker with a timeout. Should the feature return, the contract stands: model returns pattern plus test cases, client validates against the sampled column, compiled rules are stored and versioned so evaluation never calls the model.
HTML5 Canvas / WebGL via PixiJS or React Flow
§6
The core interaction is typing into cells with rich text, IME, selection, accessibility and copy/paste, all of which the browser provides only for DOM text. A Canvas grid must re-implement them. PixiJS is a game renderer with no text-editing story; React Flow is a node-graph library that does not virtualise grids. The prototype achieved pan, zoom and semantic LOD with a single CSS transform on a DOM layer.change DOM-first: one transformed layer for tables and graphs, virtualised as above. Reserve Canvas for what it is good at: gridlines and ruler backgrounds, and DAG connecting edges once they number in the hundreds, drawn on a separate non-interactive layer under the DOM. Revisit WebGL only if profiling shows the DOM layer missing its budget.
Spatial hashing / quadtrees
§6
Tables snap to a uniform lattice (§12). Every object’s bounds are integer grid rectangles, so viewport culling is arithmetic on row and column ranges; a quadtree adds cost without benefit until objects overlap or free-float.change Replace with a sparse lattice index: two ordered maps (column → objects, row → objects) plus per-object grid bounds. Visible set = objects intersecting the viewport’s row and column ranges. The same index serves A1 address resolution, hit-testing and pointing mode.
Semantic zooming
§6
Holds up. The three tiers (micro, meso, macro) worked in the prototype; the missing piece is that text should not be laid out at all below the macro threshold.keep Keep. Specify the thresholds as scale bands, skip cell text below the macro band, and quantise the scale into buckets so the layer re-renders on band crossings rather than on every wheel tick.

Choices the original spec did not make

  • Collaboration and persistence. The chrome reads “Shared”, and graphs, formulas and pulls make multi-user editing the normal case. A CRDT document (Yjs or Automerge) holding tables, cells, formats, graphs and sheet order gives offline edits, undo history and presence. The DAG evaluates over the CRDT’s current state; it is not itself persisted.
  • Stable identity. Rows, columns, tables, sheets and graphs need ids independent of position. Every reference in §13 and §14 stores ids; A1 addresses are a presentation projection recomputed from the lattice.
  • Formula language. §13 defines three forms by example. Write a grammar (arguments, quoting, escaping of @ paths containing spaces and dots, function names) and a reference parser with error positions, so the composer can highlight and the engine can refuse ambiguous input rather than guess.
  • Workers. Regex execution, fuzzy matching over large columns, and bulk re-evaluation belong off the main thread. The engine’s API should be message-shaped from the start so moving it into a Worker is a deployment change.
  • Testing. Property-based tests for the text-transform algebra (marks survive every operation) and for the dependency graph (evaluation order equals topological order; no stale reads after structural edits). Golden-file tests for the ring and coverage layouts.
  • Performance budgets. State them: 16 ms from keystroke to visible update at 1,000 visible cells; pan and zoom at 60 fps with 10,000 cells on the sheet; formula recompute under 50 ms for a 500-row dependent chain. Choices are tested against these, not against preference.

21. Platform, Delivery & Access

Compute

  • ARM throughout. Every runtime component targets AArch64: application servers and API on AWS Graviton (Fargate on ARM or EC2 c7g/m7g), the database on Graviton RDS or Aurora, caches on Graviton ElastiCache. Container images are built as linux/arm64 only; no multi-arch manifests, so nothing silently falls back to x86.
  • Dependency policy. Every native dependency (regex engine, CRDT bindings, image handling, database drivers) must ship prebuilt AArch64 binaries or build from source in CI. A dependency without an ARM build is disqualifying, not a workaround.
  • No LLM services. Section 1’s AI layer, Section 5’s natural-language-to-regex and Section 8’s semantic triggers are out of v1 scope. Smart Chips remain as static, pre-validated patterns. No Bedrock or other model endpoints are provisioned.

CI/CD on AWS CodeBuild

  • Source. The repository may stay on GitHub, but no GitHub Actions run. CodeBuild connects via the CodeStar / GitHub App connection and triggers on push and pull request webhooks.
  • Build fleet. All projects run on CodeBuild ARM compute (ARM_CONTAINER, aws/codebuild/amazonlinux-aarch64-standard) so tests execute on the same architecture that serves production.
  • Stages. (1) Verify on every PR: install, type-check, unit and property tests, lint, bundle-size budget. (2) Build on main: linux/arm64 image to ECR, web bundle to S3, content-hashed. (3) Deploy: CodePipeline promotes the same artefacts through staging then production, with a manual approval gate before production. (4) Post-deploy: smoke tests against the deployed URL; failure rolls the ECS service back to the previous task definition.
  • Infrastructure as code. CDK (TypeScript) defines every stack, including the CodeBuild projects themselves, so the pipeline is reproducible from an empty account.
  • Cost controls. Build caching (S3 cache for dependencies, ECR layer cache), PR builds limited to Verify, and a small ARM instance size by default. No always-on runners.

22. Column Data Formats & Numeric Formulas

The Cell inspector’s Data Format (Section 18) becomes a real type system applied per column, with cell-level override.

FormatOptionsBehaviour
AutomaticInfers Number, Currency, Date or Text from the typed value.Default. Inference never rewrites the stored text; it only picks the display and the numeric parse.
TextCase presets from Section 3 (Title Case, UPPERCASE, lowercase, Trimmed).Never numeric; excluded from =Sum().
NumberDecimal places (0–6), thousands separator, negative style (− / parentheses / red), percentage.Right-aligned. Stored value is the parsed number; display re-renders on format change without re-typing.

  • Column scope. Format is set on the column header (inspector or header menu) and inherited by every cell; a cell may override. Appended rows inherit the column format.
  • =Sum(). Accepts a range (B2:B14), a list of addresses, @ paths, or a whole column (B:B). Offered in the = dropdown only when the selected cell’s column is Number or Currency. The result cell takes the operands’ format. Blank cells count as zero; a Text cell inside the range produces ⚠ text in range on the result and highlights the offending cell.
  • Reference highlighting. As Section 13: with a =Sum() cell selected, its range renders as one outlined block on the canvas and each discrete address as its own outline, colour-keyed to the expression. During editing, typing or extending a range updates the outline live, and clicking cells on the canvas inserts their addresses at the cursor.
  • Footer totals. A Number or Currency column may show =Sum() of its visible rows in the table footer (Section 18 footer rows), respecting the active filter.

23. Languages, Keyboards & Locale

GeDe accepts input from English (US, UK, India), Tamil, Hindi and Telugu keyboards, and formats numbers and dates for each locale. Cell text is Unicode throughout; the requirement is that composition, shortcuts, rendering and formatting all behave correctly for each.

The cell editor listens to compositionstart / compositionend and ignores Enter, Tab and arrow keys while composing (also keyCode 229 and isComposing), so a half-formed conjunct is never committed or split across cells.

  • Typing to edit. Any printable Unicode letter, number or punctuation (\\p{L}\\p{N}\\p{P}) begins overwriting the selected cell; Process / Dead keys open the editor and hand the composition to the IME.
  • Rendering. The UI font stack falls back to Noto Sans Tamil, Devanagari and Telugu so conjuncts, vowel signs and matras shape correctly; the root element carries lang for the active locale so browsers pick the right shaping and hyphenation.
  • Sorting and search. Lexical sort uses Intl.Collator for the active locale (numeric, base sensitivity), so Tamil, Hindi and Telugu strings order by their script’s rules rather than by code point. Fuzzy filter operates on grapheme clusters, not UTF-16 units.
  • Number and date formats. Column formats (Section 22) render through Intl.NumberFormat and Intl.DateTimeFormat for the active locale: Indian locales group as lakh and crore; date patterns follow the locale; Tamil, Hindi and Telugu show localised month names in the long form.
  • Chrome and formulas. Formula function names (Concat, Sum) and A1 addresses stay ASCII in every locale; @ entity paths may contain any script. Menu and inspector copy ship in English for v1 with string tables ready for translation.
  • Picker. A locale control in the chrome switches language, keyboard expectations and formats at once and persists per user.
